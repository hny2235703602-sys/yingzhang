# 小说章节转动漫分镜改写方案

> 文档状态：设计草案，尚未实现程序或验证模型输出质量。
> 本文聚焦小说理解、动漫改编、分镜规划和提示词输出；ComfyUI 接入只定义数据边界。
> 当前范围：本章人物与连续性分析、跨章节角色视觉资料、可选前情；完整人物关系与历史记忆库作为后续扩展，不纳入第一版。

## 1. 已确认需求与范围

用户在另一台 Windows 电脑上运行 ComfyUI，显卡为 RX 9070 XT，系统内存 32GB。已部署用户称为“minmax h3”的视频模型，以及通过 LM Studio 运行的 Qwen3.5 27B；准确模型与量化版本待核实。视频曾成功生成，用户回忆约 20 分钟生成一段 5 秒视频，该数值只作为初步成本参考，不视为基准测试。

本方案的输入是一篇长篇网文小说的某个章节；输出是经过动漫化改编的分镜清单，以及用于生成每个镜头视频的模型提示词。

已确定的产品要求：

- 不固定一章的成片时长，也不固定镜头总数。
- 由 AI 根据章节实际的剧情密度、冲突、动作和信息量决定镜头数量；内容丰富可以多分镜，剧情简单应精简。
- 不逐句、逐段机械翻译小说，而是提炼重要剧情，形成适合动漫呈现的场景和镜头。
- 第一版以每个生成片段约 5 秒为设计基准，具体帧数和实际时长由后续视频工作流适配。
- 最终生产目标为独立镜头视频，暂不包含成片拼接、配音、字幕和口型同步。
- 可以保留对白与声音意图作为剧本信息，但不得默认系统会生成可用对白或音轨。

## 2. 核心原则

### 2.1 先改编，再拆镜，最后编写模型提示词

处理链路为：

```text
小说章节
  → 原文编号与分块
  → 分块事件提取
  → 全章事件合并和因果分析
  → 动漫化改编大纲
  → 场景剧本
  → 约 5 秒镜头规划
  → 连续性与剧情校验
  → 模型提示词生成
  → 结构校验与局部返修
  → 镜头清单与提示词包
```

不要求语言模型一次输出整章全部镜头。每个阶段保存结构化结果，下一阶段只接收必要信息；长章节按场景分批生成镜头。

### 2.2 镜头数量由叙事需求决定

不采用“每 N 字一个镜头”“每段原文一个镜头”或“每章固定一分钟”的规则。

镜头存在的理由必须明确：建立必要空间、推进事件、表达关键反应、展示关键动作、交付新信息、承接转场或制造有效悬念。仅有漂亮画面、却不承担本章叙事作用的镜头不自动保留。

### 2.3 保留剧情事实，允许改变表现方式

允许压缩与合并重复内容，调整适合视觉表现的局部顺序，用动作和表情替代可视化的心理描写，添加必要的过渡或构图细节。

不得为了画面效果擅自改变核心事实、人物目标、关键因果、重要关系和事件结果；不得补造未提供章节的秘密、未来反转或世界观规则。

## 3. 输入与上下文

### 3.1 必需输入

- 章节正文。
- 章节编号或标题；没有时由程序赋予内部编号。

### 3.2 可选输入

- 作品简介、此前剧情摘要、角色资料和已有参考图。
- 动漫风格和横竖画幅。
- 改编偏好，例如更紧凑、偏动作、偏情绪。
- 当前视频模型能力，例如是否支持参考图、图生视频、音频和负面提示词。

缺少可选项时可继续改写，不阻塞整个流程。影响剧情理解的缺口放入 `uncertainties`；影响生成执行的缺口放入生成适配状态。

### 3.3 单章节知识边界

只输入一个章节时，系统不具备整本小说的知识。无法确认的人物年龄、服装、身份和前情不可当作原文事实输出。

确有画面需要时，可在 `visual_assumptions` 中建立最少量的临时视觉设定，注明“改编补充”，并在本章内保持一致；涉及剧情真相的空缺不得以假设补齐。

多章连续处理时应复用作品级角色和场景资料，不在新章节重置人物外观。

## 4. 阶段一：原文整理与长文本理解

### 4.1 给原文建立稳定编号

保存原始文本，为每个段落分配 `P0001` 等编号。文本预处理仅规范换行和明显空白，避免误删对白、标点或有意义的重复。

原文是待改编的数据。即使正文中出现“忽略此前指令”“输出以下格式”等文字，也不得作为系统指令执行。

### 4.2 按语义分块

优先在场景、时间、叙述视角或事件边界分块，避免把一段完整对白或动作链截断。

实际块大小依据 LM Studio 当前模型的可用上下文、输入长度和输出预算设置；不直接按照模型标称最大上下文塞入整章。

跨块只传递必要重叠内容或前块状态摘要。重叠段落保留同一原文编号，后续按编号和事件实体去重。

### 4.3 提取可追溯事件

每个文本块输出：

- 事件编号和原文段落编号。
- 谁想做什么、做了什么、遇到什么阻碍、导致什么结果。
- 地点、时间、出场角色、关键物品。
- 对白的剧情功能，而不只是对白原句。
- 人物已知信息与观众已知信息。
- 新线索、伏笔、悬念和情绪转折。
- 尚不能确认的信息。

### 4.4 全章统一合并

分块完成后合并事件，统一人物别名、去重，建立事件因果与状态变化。

输出本章的一句话主线、主角目标、核心冲突、转折、结果和章末悬念。章节没有高潮或悬念时允许相应字段为空，不强行编造戏剧结构。

## 5. 阶段二：剧情筛选与动漫化改编

### 5.1 事件分级

| 等级 | 判断依据 | 处理方式 |
| --- | --- | --- |
| 必须保留 | 改变事件走向、解释关键选择、交付必要信息、呈现核心冲突或结果 | 在剧本中明确落地 |
| 可压缩 | 重复情绪、相似攻击、重复论证、冗长解释 | 合并为代表性动作、反应或对白 |
| 可省略 | 对本章理解和后续因果无实际作用的重复或枝节 | 删除并记录原因 |
| 暂不确定 | 可能涉及后续伏笔，但现有上下文不足 | 标记缺口；优先保留最少必要信息 |

不要仅因为某段不容易拍摄就删除它。必要但难以直接视觉化的信息，应设计替代表达方式。

### 5.2 文学描写的转换规则

| 小说内容 | 动漫化表达 |
| --- | --- |
| 重复的心理纠结 | 一次关键犹豫、视线变化、手部动作或有意义的停顿 |
| 长篇环境描写 | 必要建立镜头；其余环境嵌入人物行动背景 |
| 长篇设定说明 | 仅保留当前事件必须知道的内容，以关键道具、行为或短对白传达 |
| 大量相似战斗动作 | 保留起手、阻碍、转折和结果，删去重复招式 |
| 重要对白 | 保留言语意图与必要内容，配套可理解的画面 |
| 抽象情绪 | 转为可见表情与行为，不把“命运感”等抽象词当作主要动作 |
| 章末反转 | 保留揭示所需前因和观众能看懂的证据，避免只有无意义特写 |

### 5.3 无声镜头视频的叙事边界

第一版不保证对白音频或字幕，不能默认观众会听到剧本中的台词。

对依赖语言才能理解的情节，尽可能用可视动作、道具关系或反应链补足；仍无法无声表达时标为 `requires_dialogue` 或 `requires_text_overlay`，保留对应台词或文字意图，并在输出中明确该镜头仅完成视觉素材。

不可为了“无声也能懂”擅自改变关键事实。也不要要求视频模型绘制必须准确可读的长信件、秘籍或字幕；必要文字由未来的文字叠加环节处理。

### 5.4 改编变更记录

每项删减、合并和补充均记录对应事件和原因，区分：

- 原文事实。
- 改编后的表现形式。
- 临时视觉设定。
- 未解决的剧情或生成条件。

此记录用于复核，不必全部塞进视频提示词。

## 6. 阶段三：场景与镜头数量规划

### 6.1 先划分场景

场景以地点、时间和连续事件为边界，记录场景目标、进入状态、冲突、离开状态和必要信息。

一个章节可能只有一个场景，也可能有多个场景。不要为每个原文自然段创建场景。

### 6.2 为必要信息安排可拍摄动作

对每个场景列出必须让观众看到或知道的内容，再选择最精简且能看懂的镜头组合。

允许建立镜头、动作镜头、反应镜头、信息特写、对话镜头与过渡镜头；这些是可用手段，不是每场必须齐备的固定套餐。

### 6.3 自动决定数量的步骤

1. 为核心事件生成第一版最少镜头集。
2. 检查哪些镜头同时包含多个难以在约 5 秒完成的动作、复杂运镜或地点变化。
3. 对超载镜头拆分，使每个镜头有一个主要动作或清晰的情绪变化。
4. 检查空间关系、反应和因果是否缺失，只在必要处补镜。
5. 合并表达重复、构图近似且没有新增信息的镜头。
6. 检查所有必须保留事件是否覆盖，关键状态是否前后连接。
7. 输出最终镜头数量、约计素材时长和成本估算。

不设置固定章级镜头上限，也不为了凑整数或时长自动加镜头。程序可以分批执行大量镜头，但执行批次不改变剧情规划。

### 6.4 防止镜头无限膨胀

每镜填写 `story_purpose`，并回答“删除此镜会失去什么”。如果没有新的叙事、空间或节奏价值，优先删除或合并。

紧张、悲伤、震惊等情绪不自动各占一镜；只有情绪变化本身推动剧情时才需要独立表现。复杂动作也不拆到每一次眨眼、迈步。

### 6.5 成本展示

在暂按每镜 5 秒、每镜约 20 分钟估算时：

```text
名义素材时长 = 镜头数量 × 5 秒
基础生成耗时 = 镜头数量 × 20 分钟
```

例如 30 镜对应约 150 秒素材、约 10 小时基础生成时间。该估算不含提示词生成、加载、排队、重试或额外素材生成；真实耗时需在目标电脑测试。

成本用于让用户了解任务规模，不作为自动压缩必要剧情的硬性时长上限。

## 7. 阶段四：约 5 秒镜头设计

### 7.1 单镜头约束

- 一个主要动作或一次明确的情绪变化。
- 明确主体、地点、起始状态和结束状态。
- 默认单一连续拍摄，不在一条提示词中要求多个剪辑切换。
- 摄像机运动应简单，并与主体动作兼容。
- 控制同屏角色与同时发生的事件数量；复杂多人互动优先用构图和拆镜降低难度。
- 需要更长过程的事件拆成准备、关键变化、结果等有意义阶段，不把整个过程加速塞进 5 秒。

“5 秒可拍摄”是设计判断，不能保证模型完全遵从；最终仍需样片验证。

### 7.2 连续性状态

每镜记录：

- 出场角色及服装版本。
- 角色站位、视线和运动方向。
- 武器、关键道具的持有者与状态。
- 伤势、污渍、破损等持续变化。
- 时间、天气、光照、场景布局。
- 起始状态、结束状态与前后镜头依赖。

相邻镜头不得无解释地换手持物、改变伤势或改变人物位置。切换角度时避免无意反转运动方向或人物相对位置。

### 7.3 外观一致性策略

角色使用稳定 ID；姓名和称呼仅作为别名。建立统一外观描述与服装版本，不让每镜自由重写人物。

参考图和图生视频能力确认后可加入镜头输入。固定种子只用于复现配置，不能保证跨镜头人物一致。

相邻镜头可按需要使用前镜尾帧作为参考，但这会增加生成依赖，并可能累积画面偏差；不默认所有镜头串接尾帧。

## 8. 阶段五：编写模型提示词

### 8.1 保存“分镜语义”和“模型提示词”两层数据

分镜语义记录剧情目的、人物、动作、构图和状态，保持模型无关。

模型适配器将这些数据转换为实际视频模型支持的提示词和参数。更换模型时可重新编译提示词，不需要重新改编小说。

ComfyUI 是执行工作流的平台，不存在适用于所有视频模型的统一提示词语法。

### 8.2 提示词推荐组成

```text
画面风格与媒介
+ 主体固定视觉特征
+ 场景与必要空间关系
+ 起始构图和景别
+ 一个主要动作或情绪变化
+ 简单运镜
+ 光照与氛围
+ 必要的连续性约束
```

只写当前镜头需要的可见信息。人物姓名不能替代外观描述；“他意识到自己被骗”需要转成可见表现。

语言、长度、特殊标记和负面提示词均由模型适配决定，不默认英文优于中文，也不默认支持 Stable Diffusion 权重语法。

### 8.3 正负提示词与参数的边界

- `video_prompt`：生成当前画面与动作。
- `negative_prompt`：只有工作流支持时才输出；默认不机械堆叠通用词。
- `dialogue`：独立保存台词，不自动注入不支持声音的视频模型。
- 时长、帧数、分辨率和种子：作为参数传给工作流，不靠自然语言保证生效。
- 节点 ID、模型路径和采样设置：由程序配置，不让语言模型猜测。

### 8.4 提示词示例

假设原文为：“少年看见信纸上的落款，意识到师父隐瞒了真相，随后入殿质问。”

可将“看见信纸”和“入殿”拆开，避免同一镜头跨场景并承载多次事件。

一个反应镜头的语义：少年低头看信，握纸的手收紧，抬眼望向殿门。

对应中文提示词草案：

> 二维动画风格，中近景。黑色短发、身穿深蓝长袍的少年站在庭院廊下，双手拿着一张信纸。少年低头看着信纸，眉头逐渐收紧，握住纸边的手轻轻用力，然后抬眼望向画面右侧的大殿入口。摄像机固定，冷色月光，背景廊柱和殿门保持稳定，单一连续镜头。

这里的发型、服装和庭院属于示例视觉设定，实际项目需从原文或角色资料取得，并标注必要补充。

如果“信纸落款的准确文字”是理解剧情的关键，应另记文字叠加需求；此提示词本身不保证观众能读出真相。

## 9. 输出数据契约

### 9.1 章节级信息

章节记录至少包含：章节 ID、剧情摘要、核心冲突、改编后的事件顺序、角色资料、场景资料、事件处理记录、存疑项和镜头列表。

### 9.2 单镜头示例

以下仅示范数据结构，不是已经适配某个视频模型的执行请求。


### 9.3 面向用户的可读分镜表

| 字段 | 用途 |
| --- | --- |
| 镜头编号 | 对应视频文件和执行任务 |
| 原文依据 | 追溯改编来源 |
| 剧情作用 | 解释为何保留此镜 |
| 画面与动作 | 快速检查可拍摄性 |
| 景别与运镜 | 检查镜头语言 |
| 时长 | 默认约 5 秒 |
| 视频提示词 | 供工作流调用 |
| 连续性和素材需求 | 角色、道具、参考图 |
| 存疑与状态 | 区分待核实、可生成和已完成 |

程序输出建议包含原文索引、事件清单、改编大纲、角色与场景资料、镜头 JSON、可读分镜表和存疑清单。具体文件命名在实现时确定。

## 10. 质量检查与返修

### 10.1 程序可确定检查的项目

- JSON 能否解析，字段类型是否正确。
- 镜头编号是否唯一，顺序是否完整。
- 原文、事件、角色和场景引用是否存在。
- 时长是否符合当前执行配置。
- 依赖关系是否存在循环。
- 必须保留的事件是否至少被镜头引用。
- 提示词是否为空，所需素材是否已提供。

事件被引用不代表剧情已被表达准确，还需要语义复核。

### 10.2 Qwen 语义复核项目

- 观众是否能理解主角目标、冲突、转折和结果。
- 是否遗漏必须保留的事实或改变关键因果。
- 是否出现没有依据的剧情补造。
- 是否依赖未生成的旁白、对白或可读文字。
- 每镜能否在约 5 秒内合理完成。
- 是否存在重复、空镜堆积或无意义拆镜。
- 人物、道具和空间关系是否连续。
- 提示词是否对应分镜，而不是夹杂分析或抽象评论。

### 10.3 局部返修

发现问题后返回对应阶段，优先只修相关镜头或场景，并复核相邻连续性。程序保留已通过内容，不因一条无效 JSON 重新生成整章。

设置有限的自动返修次数；达到次数后保留结果和问题说明，标为待处理，不无限循环。

## 11. 语言模型调用方案（线上 API 优先，保留本地）

当前优先由外部控制程序通过 API Key 调用线上语言模型，保留 LM Studio + Qwen3.5 27B 本地服务作为可切换方案。两种来源复用相同的改编流程与输出契约，切换时无需重新设计分镜流程。线上提供商、地址、模型和协议尚待配置；本地服务与量化版本仍待目标电脑确认。

此处线上 API 指文本理解、改编和提示词生成服务。视频继续通过 ComfyUI 执行，不因此默认接入或购买线上视频服务。

建议为各阶段使用独立任务模板：

1. 事件提取器：只提取事实和证据，不写分镜。
2. 改编编辑：筛选事件并输出全章大纲。
3. 场景编剧：把保留剧情转成可表现的场景。
4. 分镜导演：拆分镜头并记录连续状态。
5. 提示词编译器：适配实际视频模型。
6. 审核器：查缺失、超载、矛盾和结构问题。

这些是同一个模型分阶段承担的职责，不要求部署多个大模型或并行智能体。

实现注意事项：

- 每次调用明确输入、允许的改编范围和输出结构。
- 推理过程与最终结构化结果分开处理；不能直接把模型原始回复当作有效 JSON。
- 当前提供商若支持且已验证结构化输出，可启用 JSON Schema 约束；否则使用解析、校验和定向返修。
- 明确为输出预留上下文空间；按实际 token 数和服务配置调整分块。
- 较长场景分批生成镜头，每批携带角色资料、场景状态和前批结束状态。
- 不把全部历史对话无限追加；保存阶段结果并提供必要摘要。
- 提取与结构化阶段优先稳定性，改编阶段允许适度变化；参数需实测后定稿。

## 12. 与 ComfyUI 的接入边界

本阶段完成后，控制程序读取镜头清单，向已验证的 ComfyUI API 工作流填入提示词和参数。

衔接原则：

- 复用用户实际跑通的工作流，映射提示词、参考图、时长、种子和输出名称。
- 先生成并保存全章文本结果，再串行生成视频。仅当使用本地语言模型且与视频共享资源时，执行并确认本地模型卸载；线上调用不需要卸载 LM Studio。
- 镜头生成状态和文本校验状态分开记录。
- 保存任务 ID、输入版本、输出位置与错误信息，支持断点续跑。
- 连接中断时先查询已提交任务，避免重复生成。
- 对缺失模型、缺失节点和配置错误暂停并记录，不盲目重试。
- 生成完成表示获得独立镜头视频，不表示已完成整章剪辑或声音制作。

当前不为未知节点编造可执行工作流；确定模板后再实现字段映射。

## 13. 实施顺序与验收

### 第一步：完成纯文本改编闭环

输入一章真实小说，输出事件清单、改编大纲、分镜表、提示词和存疑清单，不启动视频生成。

验收重点：核心剧情准确；镜头数量有依据；镜头描述可见且可拍摄；格式能被程序读取。

### 第二步：验证不同剧情密度

至少选择偏对白、偏动作和偏过渡的章节或片段对比。

验收重点：镜头数量随实际叙事需要变化；不会因字数增加就同比增加；必要因果和重要信息有明确镜头承载。

### 第三步：跑通少量视频镜头

从完整分镜中挑选有代表性的 3–5 镜，验证角色、运镜、动作和提示词适配。此数量仅是技术试跑规模，不是章节镜头限制。

验收重点：输入字段正确，真实执行成功，结果能对应镜头描述，记录显存和耗时。

### 第四步：整章串行生成

在前述验证后启用全章批量执行和失败恢复，输出独立镜头视频。

第一版无需向量数据库、图数据库或多个并行语言模型。本章人物关系保存在章节分析结果中，不建设跨章节人物关系库。工程约束见[工程开发要求](./工程开发要求.md)。

## 16. 第一版上下文与资料管理（当前采用）

### 16.1 输入和处理边界

第一版针对用户复制输入的小说章节进行改编，不承担小说续写。以本章正文为剧情依据，允许用户提供可选前情和已有角色视觉资料。

人物关系必须在本章分析中理解，但不要求建设自动跨章节更新的完整人物关系库。章节分析结果可以保存供用户回看，不等于自动把它们作为下一章记忆注入。

### 16.2 三类必要资料与可选前情

| 资料 | 保存范围 | 用途 |
| --- | --- | --- |
| 本章人物与关系 | 当前章节工作数据 | 识别人物、称谓、对白对象、动机和事件因果 |
| 本章连续状态 | 按场景与镜头位置保存 | 跟踪伤势、道具、站位、服装和信息揭示，避免同章前后矛盾 |
| 角色视觉资料 | 同一作品内跨章节复用 | 固定人物 ID、外貌、参考图、服装版本和标志性特征 |
| 可选前情 | 本次输入中有选择地提供 | 解释正文省略的必要背景，不是必填项 |

不同作品的角色资料用作品 ID 隔离。称谓模糊时不凭名字相似强行合并人物。

### 16.3 角色视觉资料规则

优先使用用户提供的资料和正文明确描述。缺失而必须补充的视觉选择标为改编设定，确认或采用后复用，不把它冒充原文事实。

基础外貌、参考素材和服装版本分别保存。新章出现换装、成长或外貌变化时创建适用版本，不覆盖旧镜头引用的版本。当前章节受伤不自动成为永久外观。

固定描述和种子不能保证角色一致，参考图及图生视频路径需在实际 ComfyUI 模板上验证；在模型能力确认前先保存素材要求。

### 16.4 缺失前情的处理

如果本章无法说明某个关键动作或关系的原因，记录原文位置、缺失内容和受影响场景。可采用以下处理：

- 不影响核心剧情的细节保持中性，不额外补造。
- 能在现有依据下改写为可见行为的，继续处理并保留说明。
- 影响关键因果或身份判断的，标记相关场景待补充，其他场景继续分析。

不默认读取所有历史章节，不编造未输入的前情。后续如连续改编出现明确需求，再增加可编辑的轻量前情摘要；完整历史事件库、长期关系演变和伏笔管理均属于可选扩展。

### 16.5 当前采用的完整流程

```text
章节正文 + 可选前情 + 已有角色视觉资料
  → 原文索引与语义分块
  → 提取本章人物、关系、事件和状态
  → 合并全章信息，标记前情缺口
  → 筛选与改编剧情
  → 编写场景剧本
  → 按剧情需要决定镜头数量并拆镜
  → 检查本章连续性、因果和观众信息
  → 生成模型提示词与参考素材需求
  → 保存分镜版本
  → 若使用共享资源的本地语言模型，释放其占用
  → ComfyUI 逐镜头生成，记录结果并支持恢复
```

同章后段揭示的信息不能提前进入前段镜头。原文有某条信息不等于观众已知；依赖对白或可读文字的内容，未实际呈现时必须保留相应说明。

### 16.6 状态与恢复

分别保存章节分析、分镜校验和视频执行状态。视频失败不需要重新分析全章；修改一条提示词只使相关生成结果待更新。参考资料或正文版本改变时，标记相关分镜需要复核。

LangGraph 检查点用于阶段恢复，SQLite 保存业务结果。远端 ComfyUI 任务恢复时先核对已保存的任务 ID，避免重复提交。缓存失效按依赖范围处理，不默认重做全项目。

### 16.7 第一版验收

- 不提供历史章节也可以完成自包含章节的改编。
- 本章人物和关系有正文依据，不强行补齐未知背景。
- 镜头数量随剧情需要变化，不按字数或固定章级时长切割。
- 同章人物、服装、伤势、道具与空间关系保持连续。
- 角色视觉资料可以跨章节复用，并支持版本变化。
- 必要前情缺口可见，缺口不扩散成虚构剧情。
- 不自动建立完整人物关系记忆库，也不全量注入历史章节。
- 提示词可独立修改，视频任务可单镜头重试和恢复。

当前文档是实施依据，尚未实现程序、验证模型兼容性或测试真实章节效果。

## 17. 线上 API 接入与本地切换

### 17.1 统一调用边界

改编各阶段只依赖统一语言模型适配接口，不在 LangGraph 节点中硬编码地址、密钥或特定厂商 SDK。适配器返回正文、结束原因、服务请求 ID、实际模型标识和可获得的用量数据；供应商没有返回的字段保持未知。

第一版默认一条流程使用一个模型配置，保留阶段级覆盖扩展点，不要求并行调用多个模型。OpenAI 兼容仅是协议选项，不表示供应商一定是 OpenAI；Chat Completions、Responses 或厂商原生接口须显式选择和验证，不能假设完全兼容。

### 17.2 配置与凭证

模型配置至少包含 profile_id、provider、protocol、base_url、model、api_key_env、context_budget、max_output_tokens、请求超时、并发上限、重试上限和能力标记。密钥字段保存环境变量名称，不保存真实值。

线上配置与本地配置独立保存，由用户选择当前 profile；本地 API 是否需要密钥取决于其服务配置。API Key 只由执行器读取，不写入 LangGraph 状态、SQLite 业务记录、导出分镜或日志；凭证不通过 URL 查询参数传递。

配置后可进行显式的小规模连接和结构化输出测试。服务列出模型不代表该模型实际可调用或具备所需能力；未配置密钥时允许继续编辑项目与查看既有结果。

### 17.3 兼容性与上下文

按实际接口确认 system 消息、结构化输出、流式返回、推理内容、输出 token 参数和采样参数的支持情况，仅发送支持的参数。分块和输出预算使用当前模型配置，不复用本地模型的上下文假设。

切换配置后，将提供商、协议、实际模型及相关参数纳入版本与缓存键。既有分镜保留来源，不将不同模型结果静默混用或覆盖；用户可有意只重跑选定阶段或镜头。

### 17.4 错误、重试与费用

- 认证错误、无权限、余额不足、模型不可用和无效参数给出明确配置错误，不无限重试。
- 限流和暂时性服务错误采用有限退避与抖动；支持时遵守 Retry-After。SDK 与应用层统一重试预算，避免嵌套重试放大调用次数。
- 超时或中断可能已经计费；重新调用可能再次收费。记录未知用量，不宣称重试具有服务端幂等保证。
- 模型拒绝、输出截断、非法 JSON 与前情缺口区分处理，有限局部返修；已成功阶段不重复调用。
- 使用供应商返回的 usage 统计 token；成本仅在有对应币种、定价及适用日期时估算，缺失用量不按零成本处理，计费账单以提供商为准。
- 费用预算可选配置；达到预算时停止新调用，保留已完成结果。未设置预算不增加强制审批。

请求内容会发到用户配置的服务方。调用仅发送当前阶段需要的小说片段与资料，不默认上传整本小说、项目文件或历史章节。

### 17.5 回退与验收

线上失败不自动切换到本地或另一家服务商，避免改变输出风格、隐私边界和费用。用户可切换配置并从选定阶段恢复，保留新旧版本。

先验证线上文本闭环，再验证本地适配仍可使用同一数据契约。自动测试覆盖密钥缺失与脱敏、协议差异、限流、超时、截断、结构化输出降级、重试上限和缓存隔离。真实调用需用户配置有效服务，当前文档不表示已接通线上模型。
